项目介绍

背景与目标

我关注的问题是：业务文档、历史代码和实验记录中已经存在的算法经验，能否被整理为可检索的能力知识，并进一步转化为经过验证的算法代码？

直接让大模型生成一个分类器，可以得到代码，但实现依据、验证过程和后续复用往往分散。我希望把这些步骤连接起来：任务开始时利用已有知识，任务执行时记录生成与修复过程，任务结束后把算法版本和验证经验重新沉淀到知识库。

因此，我设计了 Capability Forge 算法能力工厂原型。它接收自然语言能力描述，输出可运行代码、训练模型、验证报告和更新后的知识图谱。

我的主要工作

我首先选择客户流失预测作为主场景，整理模拟业务文档和历史代码，定义输入字段、标签、预处理约束与评价指标。随后将 Markdown 分段抽取、Python AST 抽取和 LLM 知识抽取接入同一存储结构，为每条知识保留来源、原文片段和内容摘要。

在工作流上，我将需求理解、知识检索、方案规划、代码生成、验证、修复和结果回写拆成独立环节。模型负责给出需求结构、候选计划和代码，宿主程序负责检查契约、执行算法和计算指标。生成结果不直接决定验证结论。

在验证上，我采用固定随机种子的训练、验证、测试划分。验证集用于修复和候选选择，最终测试集用于评估选定版本。同时检查未知输入、缺失数据、概率输出、重复预测和模型保存重载。

我还接入客服工单紧急程度分类，复用原有工作流，替换任务插件、输入契约、算法空间和验证配置。这个过程暴露了 DataFrame 与文本序列的接口问题，我保留了失败记录，并通过显式接口补丁完成半自动验证。

运行结果

客户流失任务完成了真实 GLM 的规划、代码生成和反馈修复。修复演示由宿主显式注入未知类别缺陷，再由模型根据验证反馈修复。最终选择逻辑回归，测试 ROC-AUC 为 0.7829，F1 为 0.6432。

文本任务比较字符 TF-IDF 与逻辑回归、多项式朴素贝叶斯的组合。在开发阶段完成输入接口修正后，两个候选均通过验证，最终选中逻辑回归，测试 ROC-AUC 为 0.8701，F1 为 0.8765。这个案例属于半自动修复，GLM 原始自主运行的失败状态保持不变。

项目归档了 141 项自动化测试通过记录，并完成提交包解压后的文本半自动复现。

当前范围与后续方向

当前原型支持两种固定输入契约的二分类任务，提供 CLI、候选比较、多轮修复、图谱可视化、版本记录及插件扩展。系统采用串行多角色调度；执行隔离目前是 AST 检查与受限子进程。

下一步，我计划构建固定任务集，在相同模型、数据与调用预算下比较直接生成、知识检索增强和失败经验增强，分析首次通过率、修复次数、最终通过率与调用成本，再进一步完善执行隔离和任务扩展。

算法能力工厂技术报告

1. 问题定义

本项目的输入是自然语言算法能力描述，以及可供复用的业务文档和历史代码；输出是算法源码、模型产物、验证报告和能力知识记录。我把系统划分为两个相互连接的过程：一是从材料中抽取能力知识，二是利用知识生成、验证和沉淀算法。

主任务为客户流失预测，迁移任务为客服工单紧急程度分类。两者都是二分类，但输入分别为结构化表格和文本，适合检验工作流能否复用。

2. 技术选择与架构

我采用 Python 实现显式工作流，用 SQLite 保存属性图和运行记录，用 scikit-learn Pipeline 组织预处理与分类器。真实模型后端采用 GLM-4.7-Flash，离线后端使用显式规则和模板。入口采用 CLI，以降低环境部署成本。

3. 知识抽取与图谱

我设计了 Capability、Source、Knowledge、Function、Requirement、Strategy、AlgorithmVersion、ValidationRun、Metric、Environment 和 FailureCase 等节点。关系包括 SUPPORTED_BY、ADDRESSED_BY、IMPLEMENTED_BY、VALIDATED_IN 和 REUSED_EXPERIENCE。

Markdown 按二级标题切分，Python 文件通过 AST 提取顶层函数、注释和导入依赖。LLM 抽取时，我先为材料片段编号，再要求模型引用 source_chunk_id。宿主依据编号补入原文与行号，并拒绝未知编号和冲突引文。这样能够核对来源，但知识是否完整、语义是否充分仍需要后续评价。

检索结合显式条件与文本重叠：根据训练画像和需求约束，从 Requirement 经 Strategy 到达支持的 Knowledge/Function，再对结果排序。每条返回记录保留路径。历史失败经验按任务过滤，进入规划和修复上下文。

图谱以 SQLite 节点表和边表实现，同时保存运行及抽取审计表；可导出 JSON 和离线 SVG/HTML 视图。算法版本以运行、候选、尝试编号及源码 SHA256 追溯。

4. Agent 工作流

需求理解阶段输出任务、目标、指标与约束，宿主检查任务是否受支持。数据画像只基于训练集计算，包括缺失率、类别比例、字段类型或文本长度。

规划阶段输出候选算法、参数、预处理、设计理由与证据 ID。参数必须位于注册的有界空间，引用必须来自本次检索结果。代码生成阶段提供接口契约、当前候选估计器与参数，要求实现两个顶层函数：

def build_model(seed=42):
    # 返回未拟合的 sklearn Pipeline
    ...

def predict(model, frame):
    # 返回与输入行顺序一致的一维正类概率
    ...

宿主执行验证后，将旧代码、结构化失败信息和规则式修复建议交给下一轮。默认每个候选首次生成一次，最多修复两轮。输出格式错误和代码错误消耗既定预算；认证、服务和网络错误分别处理。通过校验的模型响应可以缓存，但算法验证仍重新执行。

5. 验证设计

数据以固定随机种子分层划分为 60% 训练集、20% 验证集和 20% 测试集。子进程获得训练数据和待预测特征，评估标签保留在宿主，由宿主独立计算 ROC-AUC、F1、accuracy 等指标。

验证包含四个层面：

层面检查内容
功能与计划一致性代码可执行、分类器类型、参数、预处理及随机种子
接口契约必要字段、概率长度、范围、顺序和有限值
稳定性缺失输入、逐字段及混合未知类别/未见词表、重复预测、保存重载
指标与资源配置门槛、运行超时、worker/wall 时间和 Python 分配峰值

验证通过的候选按配置指标选择，再对选中版本执行最终测试。客户流失按验证 ROC-AUC 选择；文本按验证 F1 选择。文本案例两候选的验证 F1 相同，程序保留顺序靠前的逻辑回归。

AST 导入检查、独立子进程、环境变量过滤、超时和线程限制用于减少误操作。当前没有操作系统级的文件、网络和进程隔离，部署到不可信环境仍需容器或虚拟机。

6. 案例与结果

客户流失预测

真实 GLM 案例接收缺失值、未知类别和不平衡约束，生成候选计划与算法代码。宿主对逻辑回归编码器显式注入未知类别缺陷，验证器检测后返回反馈，模型完成修复。

最终选择逻辑回归，测试 ROC-AUC=0.7829，F1=0.6432，accuracy=0.7042，12 项检查通过。随机森林原运行出现动态模块序列化问题；修正宿主加载器后，同一份源码通过验证集复核。原始报告与复核结果分别保留。

工单文本分类

文本任务采用字符级 TF-IDF，比较逻辑回归与多项式朴素贝叶斯。真实 GLM 的自主尝试出现输出格式、分类器选择和 DataFrame 输入处理错误。

开发过程中，我借助编码助手对已有代码增加 DataFrame 到 text 列的接口处理，并保留逐行补丁。两个候选随后通过验证，验证 ROC-AUC 分别为 0.8455 和 0.8369，验证 F1 均为 0.8221。最终选择逻辑回归，测试 ROC-AUC=0.8701，F1=0.8765，balanced_accuracy=0.8750，12 项检查通过。

该结果记录为 assisted_glm：它复用了真实模型源码，并包含开发阶段的外部接口补丁。复现不产生新的 API 调用。原自主尝试的失败记录保留，补丁没有修改估计器、参数或指标门槛。

测试与复现

项目归档了 141 项 pytest 通过记录，覆盖模型适配、抽取、契约校验、缓存恢复、工作流、任务插件和验证逻辑。文本半自动案例已从提交包解压后的代码与材料成功复现。

两类数据均为固定种子生成的模拟业务数据。这些结果用于验证工程流程，不用于估计真实行业泛化效果。三组真实模型小规模对照已完成：direct、knowledge 两组在知识检索前因理解响应封装失败，knowledge_repair 组最终通过。这个结果暴露了解析接口问题，不能作为知识增强效果结论。原始结果及 v4 重跑协议见 小规模对照分析。正式多条件、多种子矩阵尚待执行。

7. 开发中的问题与处理

问题我的处理
模型返回结构不稳定增加输出 schema、原始响应审计、有限纠正及单层包装解包
服务拥堵和网络中断区分业务码、网络与认证错误，设置有限退避重试及阶段缓存
动态模块无法重载在加载器中注册模块，复核原始代码，保留原失败记录
文本清洗器误用 DataFrame明确宿主调用形状，提供当前候选契约及针对性修复建议
失败日志难以复用将可归类的失败保存为 FailureCase，并按任务检索
生成结果与计划不一致由宿主检查分类器、超参数与预处理，不接受模型自报成功

我在复核中补上了三个边界：类别字段逐项注入未知值；文档更新后按已提交快照过滤旧知识；对照实验中断后使用新数据库重启，并核对协议、输入与已完成报告。旧知识和中断尝试保留以便追溯。具体机制和复现方法见 验证与状态管理修正。

我进一步将核心流程拆分为阶段函数、候选执行器、会话审计和结果输出模块，引入任务、计划、策略及验证结果契约。运行图谱、知识快照与导入分别具有回滚边界。模型结构错误仍可修复，程序内部错误则终止并报告。重构前后沿用相同 CLI 及归档案例，新增故障注入测试与云端回归配置，详见 代码重构说明。

8. 可扩展性与研究计划

任务、算法与指标具有注册接口。兼容算法可增加元数据或安装入口；新任务需实现读取、画像、接口及验证契约。当前指标选择采用高者更优，损失型指标需要进一步扩展排序方向。

后续我将建立固定任务集，在相同模型和预算下比较 direct、knowledge、knowledge_repair 三组，统计首次通过率、最终通过率、修复次数、tokens、耗时和最终性能。进一步的工作包括真实数据验证、完整代码隔离、仓库级能力抽取，以及面向算法方案的搜索策略。

输入需求保存在 text_task.txt，数据为带缺失值和标签噪声的模拟工单。我把文本输入、字符 TF-IDF 和模型检查放在任务插件中，复用同一套工作流。

五分钟项目演示讲稿

0:00–0:40　问题与目标

我实现的是一个算法能力工厂原型。我的出发点是，算法经验通常分散在业务文档、历史代码和实验记录中，单次代码生成没有把这些经验与验证结果连接起来。

因此，我将系统设计成闭环：从材料中抽取能力，理解自然语言需求，检索知识并规划方案，生成代码后独立验证，再按反馈修复，最后保存版本和经验。

本项目以客户流失预测为主场景，再扩展到客服工单文本分类。

0:40–1:20　架构与知识

我先展示材料和图谱。客户流失文档包含字段、缺失值、未知类别和评价要求，历史代码示例提供函数级经验。

抽取后，知识保留来源文件、内容摘要和原文片段。图谱还包含能力、策略、算法版本、验证运行和失败案例。

系统根据任务约束沿“需求—策略—知识”路径检索，将相关知识与历史失败交给规划角色。存储采用 SQLite，便于本地复现与导出。

展示文件：业务材料、图谱 schema、图谱视图。

1:20–2:30　客户流失真实生成与修复

这里展示真实 GLM 运行。输入需求要求处理缺失值、未知类别和类别不平衡，并比较候选方案。

规划包含算法、参数、预处理和证据 ID。模型生成代码后，宿主调用统一接口训练和检查。

为了演示反馈修复，我让宿主对生成的编码器显式注入未知类别故障。第一次验证检测到错误，GLM 根据反馈修复，下一轮通过。这里可以对比原始输出、注入版本和修复版本。

最终选中逻辑回归，测试 ROC-AUC 为 0.7829，F1 为 0.6432，12 项检查通过。测试结果没有用于修复或重选方案。

展示文件：真实报告、交接轨迹、修复后代码。

2:30–3:30　文本迁移与半自动修复

接下来是工单紧急程度分类。我复用同一工作流，将输入改为 text 列，接入字符 TF-IDF、逻辑回归和多项式朴素贝叶斯。

真实 GLM 自主尝试中，清洗器没有正确处理 DataFrame，导致样本数量不一致。我保留了失败记录，在开发阶段借助编码助手增加提取 text 列的接口补丁。

修正后两个候选通过验证，按配置的 F1 和候选顺序选择逻辑回归。测试 ROC-AUC 为 0.8701，F1 为 0.8765。这个案例记录为半自动修复，可查看原始失败与逐行补丁，也可不调用 API 重新训练复现。

展示文件：文本案例、接口补丁、完整报告。

3:30–4:20　验证与沉淀

我把验证独立放在宿主侧。模型负责生成代码，评估标签保留在宿主，指标由宿主计算；同时检查概率接口、缺失输入、未见词表、重复预测和保存重载。

运行结束后，每版源码摘要、指标、环境和失败原因写入图谱，后续任务可检索同一任务下的失败经验。算法、任务和指标也有注册接口。

技术问答

1. 这个项目解决了什么问题？

我希望把分散在文档、历史代码和运行记录中的算法经验，转化为可检索、可执行、可验证的能力。产出除了分类器，还有来源、计划、生成代码、验证结果和可复用的失败经验。

2. 与直接让大模型写代码相比，增加了什么？

我增加了知识抽取与来源记录、受约束的规划、独立验证、有限修复和结果回写。模型不能直接判定自己的代码成功，结论由宿主的检查和指标计算给出。

3. 为什么采用 SQLite？

当前图谱规模较小，我更重视本地复现和可追溯性。SQLite 用节点表、边表和 JSON 属性表达关系，并用外键保证端点存在。规模增大或查询复杂时，可以替换存储层。

4. 为什么没有使用 LangChain 等框架？

我采用显式 Python 状态机，使角色输入输出、预算和错误处理更直接。现阶段重点是验证能力闭环，后续可将独立角色接口迁移到其他编排框架。

5. 项目是不是多智能体系统？

当前是串行多角色工作流。理解、规划、生成与修复分开调用，但共享模型适配器，还没有独立自治智能体的协商与并行调度。

6. 知识图谱如何参与生成？

我把训练画像和需求约束映射到 Requirement，再沿 Strategy 找到知识和函数。结果及来源 ID 进入规划和代码上下文，历史失败按任务过滤后单独提供。路径可在图谱中核对。

7. 如何处理虚构来源？

我预先编号材料片段，要求模型引用已有编号，宿主附加原文和行号。未知编号或冲突引文会被拒绝并写入审计。来源存在不自动证明模型概括在语义上充分，后续仍需评估知识质量。

8. 如何防止数据泄漏？

我先划分训练、验证和测试集，只用训练集画像，要求预处理在训练 Pipeline 内拟合。评估标签由宿主保存，子进程返回预测。修复与候选选择使用验证集，最终测试结果不回流调参。

9. 为什么检查模型保存重载？

内存中能预测不等于产物可复用。项目遇到过自定义类的动态模块注册问题，导致序列化失败。我修正加载器并复核同一份源码，因此保留了保存重载检查。

10. 真实 GLM 的修复证据是什么？

客户流失案例中，宿主对生成的编码器显式注入未知类别故障，真实 GLM 根据反馈完成修复。该案例验证了反馈修复链路，报告明确记录了故障来源。

11. 文本任务为什么采用半自动修复？

GLM 在有限轮次内没有解决输出格式和 DataFrame 输入处理错误。我保留失败记录，在开发阶段借助编码助手增加列提取处理，再用同一验证机制评估候选。结果记录为 assisted_glm。

12. 文本候选如何选择？

文本配置按验证 F1 选择。两候选 F1 相同，程序取顺序中的第一个最大值，因此选择逻辑回归。ROC-AUC 是另一项报告指标；客户流失任务则按 ROC-AUC 选择。

13. 能否证明知识增强提高了生成质量？

当前记录证明知识和经验进入了工作流，真实模型对照尚未完成。我已实现三组实验流程，下一步固定任务、模型和预算，比较首次通过率、最终通过率、修复次数及成本。

14. 代码执行是否安全？

目前有 AST 检查、环境变量过滤、独立子进程、超时和线程限制，适合受控本地演示。公共服务还需要容器或虚拟机实现文件、网络和进程隔离。

15. 为什么使用模拟数据？

我先用固定种子模拟数据验证工程闭环，便于复现并控制缺失、类别变化和标签噪声。真实行业效果需要另行使用真实数据检验。

16. 如何接入新任务或算法？

兼容算法可扩展元数据、模板或安装入口。新任务需定义输入、读取、画像、接口和验证规则；指标可注册评分函数。任务变化不能只改提示词，还要同步扩展独立验证。

17. 141 项测试说明了什么？

这些测试检查抽取、接口、适配、缓存、工作流和插件行为，用于工程回归。真实模型能力由单独的实际运行报告记录，测试数量不代表通用成功率。

18. 下一步优先做什么？

我优先开展固定任务集上的真实模型对照，再评估真实数据和失败经验质量。完善执行隔离后，再考虑复杂方案搜索和自治协作。

八、项目概述

我实现了一个基于 LLM、多角色工作流和 SQLite 属性图的算法能力工厂原型，覆盖能力抽取、知识检索、方案规划、代码生成、独立验证、有限修复和结果回写。客户流失任务有真实 GLM 运行记录，其中修复演示的缺陷由宿主显式注入；文本分类通过任务插件接入，真实模型代码经明确标注的助手接口补丁后完成半自动验证。系统还支持多候选比较、离线图谱视图、版本追溯及规则式失败经验复用。
