# 真实模型对照实验

我使用固定的 GLM-4.7-Flash 模型比较 direct、knowledge 和 knowledge_repair 三组，保持数据、划分和每候选生成预算一致。实验任务为客户流失二分类，知识来源固定为规则/AST 抽取的同一份语料，不在实验组之间混入不同的 LLM 抽取结果。

## 运行顺序

我先运行 `benchmark-glm.cmd`，完成 baseline、seed=42 的三个单元，检查真实接口与整个实验流程。结果在 `runtime/glm/benchmark-v3/summary.md`。

随后运行 `benchmark-full-glm.cmd`。正式矩阵为三个条件 baseline、missing_high、minority，三个种子 42、43、44，以及三个实验组，共 27 个单元。每个数据集为 600 行，每组包含两个候选算法，候选最多生成三次，第一次通过后停止。正式结果单独写入 `runtime/glm/benchmark-full-v3/`，不把小规模检查计入正式统计。

两个入口都在本机终端隐藏读取密钥，不将密钥写入参数、报告或仓库。程序串行调用固定模型，不自动更换模型。拥堵或网络问题可能使实验暂停；重新执行相同入口会核对协议并跳过已完成单元，中断单元从独立数据库重启，历史尝试保留。

## 记录和分析

- `manifest.json`：固定协议、27 个单元的执行状态、原始报告位置与摘要、token 用量和组内汇总。
- `summary.md`：各单元状态、首次通过候选数、修复调用、用量及测试 AUC。
- `cells/.../attempts/.../runs/.../`：模型响应、事件、生成源码、验证报告和图谱。

我以任务最终通过率、候选首次通过率、修复调用及 API 已报告 tokens 比较工程表现。测试指标只来自最终选中版本。服务中断、模型契约失败、算法验证失败和内部程序错误分别检查；实际生成失败也属于实验结果，不为取得通过结果而手工修改候选。

相同模拟条件与种子的组间结果按单元配对。每组九个任务，三个种子生成不同模拟数据；这不等于对同一固定任务做九次独立 LLM 采样。正式分析应同时报告样本量、未完成单元、重启成本及各条件结果，不预设知识增强一定更好。

本说明提供运行协议，真实实验结果以实际生成的报告为准。当前已准备实验入口与协议；真实结果待运行完成后归档。实验运行期间保持代码、材料、依赖与验收策略固定；协议变化时使用新目录开展新实验。
