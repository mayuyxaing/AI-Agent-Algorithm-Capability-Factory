# 五分钟项目演示讲稿

## 0:00–0:35　问题与目标

我实现了一个算法能力工厂原型，把业务材料中的算法经验连接到代码生成、独立验证、反馈修复与知识沉淀。主场景是客户流失预测，另通过任务插件接入客服工单分类。

我希望每次生成除了留下代码，还留下需求、证据、计划、版本、失败原因和实际指标，方便复核与复用。

## 0:35–1:15　架构与知识

我从 Markdown 抽取材料片段，从 Python AST 抽取顶层函数和依赖；真实模型可补充带原文片段编号的事实。知识用 SQLite 属性图存储，包含来源、需求、策略、能力、版本、运行和失败案例。

工作流按理解、检索、规划、生成、验证、修复、最终测试和回写交接。知识保留历史版本，检索只使用已提交的生效集合；材料更新或删除后，旧事实退出默认检索。

展示：[业务材料](../materials/churn_business.md)、[图谱 schema](schema.md)、[代码讲解提纲](../submission/code-walkthrough.md)。

## 1:15–2:15　27 单元真实对照

我使用固定模型名 GLM-4.7-Flash，在三个模拟条件、三个数据种子和三个实验组上完成 27 个单元，每组九个任务。直接生成组通过 4 个，知识增强组通过 8 个，知识增强加修复组通过 4 个。

这轮知识增强组的流程完成率最高，修复组没有取得更高总体通过率。11 个失败中，10 个发生在规划引用校验，另一个没有有效候选。代码修复发生在规划之后，不能解决这些前置失败。

我把服务中断、重启成本和一次文件写入兼容修复单独记录。各组每次尝试的生成预算一致，但中断重启会增加累计调用，不能声称全过程总成本完全相同。

展示：[完整分析](../examples/real-benchmark/FULL-RESULTS.md)、[原始清单](../examples/real-benchmark/full-v4/manifest.json)。

## 2:15–3:15　真实反馈修复轨迹

我展示协议 v4 小规模记录中的真实修复案例。逻辑回归初版没有满足预处理计划，两轮反馈修复后通过。这里没有宿主故障注入，也没有外部手工修改源码，原始响应、每版代码和错误反馈都保留。

最终选择逻辑回归，测试 ROC-AUC 为 0.8795，F1 为 0.7200，16 项检查通过。该记录不并入 27 单元正式统计。早期另有显式故障注入案例，两个案例分开标注。

## 3:15–4:15　本地复现与跨场景

我先运行离线演示，提交相同需求，展示初版失败、有限修复、最终评估和图谱回写。这里采用 mock 模板，不把它当作新的真实 API 结果。现场命令见演示操作顺序，API 可用性不会阻断本地流程展示。

文本场景复用了工作流，替换为 text 输入、字符 TF-IDF 和二分类候选。真实模型自主尝试没有完整通过，我在开发中借助编码助手增加列提取接口补丁，形成明确标注的半自动复现。原始失败及补丁均保留。

展示：[演示操作顺序](../submission/presentation-steps.md)、[文本案例](../examples/v3/text-assisted-repair/README.md)。

## 4:15–5:00　验证、局限与下一步

我将指标计算放在宿主侧，修复与选择使用验证集，测试集只在最终选中版本上评估。接口检查覆盖概率、缺失、逐字段未知类别、重复预测和保存重载。当前已有 148 项回归测试通过，但这不等于穷举所有生成代码的错误。

项目仍使用模拟数据、固定任务契约和串行多角色编排，执行环境不是操作系统级沙箱。每组九个任务，缺少同一固定任务的多次模型采样。下一步我优先改善规划引用可靠性，并设计共享冻结前置产物的修复对照，评估真实数据和执行隔离。
