# 真实 GLM 小规模对照：协议 v3

我完成了客户流失任务 baseline、seed=42 的三组真实模型调用。每组使用相同的 600 行模拟数据和分层划分，模型为 GLM-4.7-Flash，候选生成上限相同。原始状态与模型响应保存在 [manifest.json](pilot-v3/manifest.json) 所列目录中。

| 组别 | 原始结果 | 失败位置或最终指标 | API 已报告 tokens |
|---|---|---|---|
| direct | failed | 需求理解的根字段校验失败，两次响应都使用单层 answer 封装 | 758 |
| knowledge | failed | 需求理解的根字段校验失败，两次响应都使用单层 answer 封装 | 762 |
| knowledge_repair | passed | 选择逻辑回归；测试 AUC=0.8795、F1=0.7200、accuracy=0.7667 | 22582 |

修复组的逻辑回归首次通过。随机森林候选未采用计划要求的 ColumnTransformer 字段分组，经过两次模型修复仍未通过，最终没有选中。此运行没有宿主故障注入，也没有外部手工修改生成代码。代码修复次数不能解释为“成功修复次数”。

## 解释

前两组在任何知识检索之前就已失败，因此三组的 0/0/1 通过结果不能用于证明知识增强或修复反馈的作用。修复组的成功证明该单元完成了真实模型的端到端流程，但不证明两个因素造成了组间差异。

本轮测试数据为 600 行；原有客户流失案例使用另一份数据，不能把两次 AUC 的差值解释为算法改进。服务拥堵的 1305 重试、原始响应、失败检查及失败源码均保留在原始记录中。

## 进入正式实验前的处理

我将单层、唯一 `answer` 对象的封装识别统一用于需求理解、规划和抽取；字段、代码和指标均不补写或更改。多层封装、存在其他根字段的歧义响应，以及缺失必要字段的响应仍由原有契约拒绝。同时向需求理解阶段提供显式输出 schema。

原来四个带封装的理解响应通过了离线解析复核。复核没有重新生成算法，也没有将上述两个 failed 改成 passed。这项修改适用于全部实验组，并通过新的协议 v4 启动独立实验目录：`runtime/glm/benchmark-v4/` 和 `runtime/glm/benchmark-full-v4/`。旧协议 v3 的三组结果不计入 v4 的正式统计。
