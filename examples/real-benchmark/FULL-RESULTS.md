# 真实模型正式对照结果

我使用 GLM-4.7-Flash 完成了协议 v4 的 27 个实验单元：三个模拟数据条件 baseline、missing_high、minority，三个数据与划分种子 42、43、44，以及 direct、knowledge、knowledge_repair 三组。每个数据集为 600 行。每次尝试中，每组每候选的生成上限为三次，通过后停止；理解和规划各允许一次格式纠正。

**27 个单元均已取得最终结果，16 个通过、11 个失败。** 服务中断的尝试作为历史记录保留，当前没有尚未结束的服务中断单元。小规模试跑没有并入这 27 个单元。

## 主要结果

| 组别 | 任务通过数 | 端到端通过率 | 已生成候选首次通过 | 反馈修复调用 | API 已报告 tokens，含历史尝试 |
|---|---|---|---|---|---|
| 直接生成 direct | 4/9 | 44.4% | 2/10，20.0% | 0 | 77147 |
| 知识增强 knowledge | 8/9 | 88.9% | 8/16，50.0% | 0 | 195792 |
| 知识增强加修复 knowledge_repair | 4/9 | 44.4% | 3/8，37.5% | 8 | 147031 |

候选首次通过率只统计已经完成规划并生成的候选。规划失败的任务仍计入端到端通过率的分母，但不构造不存在的候选，因此三组的候选分母不同。直接生成和知识增强组使用独立重采样，不接受前一版代码或验证反馈。

| 条件 | direct 通过数 | knowledge 通过数 | knowledge_repair 通过数 |
|---|---|---|---|
| baseline | 2/3 | 2/3 | 2/3 |
| missing_high | 1/3 | 3/3 | 1/3 |
| minority | 1/3 | 3/3 | 1/3 |

## 失败分析

直接生成组有四个任务因规划引用了不存在的知识 ID 而失败，另有一个任务在预算内没有有效候选。知识增强组有一个任务因规划引用不存在的经验 ID 而失败。修复组有五个任务在规划阶段因无效经验 ID 被拒绝。这些失败均保留在原始统计中。

本轮知识增强组的任务通过率最高；加入反馈修复没有取得更高的端到端通过率。修复组的五次规划失败发生在代码修复阶段之前，不能归因于修复反馈造成了退化。各单元独立调用模型，前置理解与规划存在采样差异，这些差异影响了最终结果。

按相同条件和种子配对，direct 与 knowledge 有四个任务共同通过、四个只有 knowledge 通过、一个共同失败。knowledge 与 knowledge_repair 有三个共同通过、五个只有 knowledge 通过、一个只有 knowledge_repair 通过。

这说明在本次九个模拟数据任务上，知识增强组取得了更高的流程完成率，尚不足以说明稳定的因果增益。三个种子对应不同模拟数据，未对每个固定任务重复采样多次 LLM。测试性能只能在有最终模型的任务上计算，不能删除失败任务后直接比较各组平均 AUC 并声称预测能力提升。

## 成本、续跑与写入修复

三组 API 已报告 token 总量为 419970，包含清单登记的九次历史尝试。未返回 usage 的服务请求、以及一次文件写入中断前没有完整保存的用量无法计入，实际消耗仍有未知部分。总 token 不等于完整推理资源消耗，也不能单独证明效率优劣：较早规划失败的任务消耗较少。中断重启会重新获得该次尝试的生成预算，因此三组满足的是每次尝试的预算上限相同，不是跨全部重启的累计生成次数严格相同；这是本轮比较的限制。

实验中发生过一次 Windows 文件原子替换的访问冲突。我仅为 `forge/util.py` 增加有上限的文件替换重试，通过恢复脚本证明其余算法、模型调用、提示词和验收相关源码未变，并校验此前九份报告摘要。原清单备份和变更记录保存在 [windows-io-hotfix.json](full-v4/windows-io-hotfix.json) 与 [原清单](full-v4/manifest.before-windows-io-hotfix.json) 中。完整说明见 [写入恢复](../../docs/windows-io-recovery.md)。原始实验不宣称全程具有同一个源码摘要。
