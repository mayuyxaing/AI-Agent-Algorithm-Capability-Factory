## 三组轨迹

直接生成组在规划时引用了未提供的知识 ID，有限纠正后仍未通过，因此没有生成算法。这个失败纳入端到端通过率，但没有可计算的候选首次通过率或测试性能。此前中断尝试中的代码不替换这个最终结果。

知识增强组的逻辑回归在第二次独立生成时通过，森林在第三次独立生成时通过。它们没有收到上一版代码和验证错误；重复生成属于独立重采样，不能记作反馈修复成功。最终按验证 AUC 选择逻辑回归。

知识增强加修复组的逻辑回归前两版未满足计划一致性检查，在第二次修复后通过。随机森林首次通过。模型修复使用真实验证反馈；没有宿主故障注入或外部手工修改生成代码。最终同样选择逻辑回归，保留测试集的 16 项检查通过。

## 解释与正式实验

本轮每组只有一个任务，直接生成组又在规划阶段失败，不能从 0/1、1/1、1/1 的结果判断知识或修复反馈带来稳定提升。两个通过单元的测试结果相同，也不能证明两种策略等效。token 用量来自 API 实际返回的 usage，不包含没有返回 usage 的失败请求，不能视为完整推理资源消耗。

我将这些结果作为小规模流程检查，正式实验单独使用 `benchmark-full-glm.cmd`，按三个条件、三个种子、三个组执行 27 个单元，输出到 `runtime/glm/benchmark-full-v4/`。正式实验不会合并这次小规模结果，运行期间保持代码、材料、环境与验收策略固定。
